# Правила для ИИ-разработчиков Sushef

1. **Приоритет:** безопасность еды и корректность рецептов важнее юмора, рекламы и правдоподобно звучащих выдумок.
2. Не создавайте фиктивных API-вызовов, не утверждайте, что тесты прошли без запуска; не заявляйте, что бот развернут без проверки Telegram.
3. Используйте ClaudeHub через конфигурацию. Не встраивайте токены, секреты, данные пользователей и пароли в код или issue.
4. Сохраните фирменный характер Сушефа: почтительный, тёплый, с частыми заслуженными комплиментами и добрым ненавязчивым юмором.
5. Соблюдайте предпочтения, явно указанные аллергены и противопоказания. Не советуйте спасать испорченную или опасную пищу. Для безопасности сначала точность, потом шутки.
6. Пользовательские записи привязаны к Telegram ID. Запретите доступ к чужим записям. Поддерживайте удаление пользовательских данных.
7. Прежде чем менять интерфейс, проверьте совместимость существующих callback_data с ботом. Тестируйте переходы, ошибки модели и JSON.
8. **GitHub Actions — дефицитный платный ресурс.** По умолчанию не используйте их для сборки, диагностики, тестов или деплоя. Выбирайте локальные средства, GitHub API и сервер. Никаких массовых запусков и тайных workflow.
9. Для спорных архитектурных изменений создавайте PR с чётким описанием последствий. Не создавайте дополнительные внешние API-расходы без нужды.
10. Первый релиз — один экземпляр polling-бота. При масштабировании переходите на webhook, миграции Alembic, транзакционные квоты и очереди; не запускайте параллельные polling-процессы.

## Обязательные правила ферментации

- Отдельно классифицировать микробную ферментацию и обработку **внешними ферментами**. Нельзя называть пищу пробиотической без подтверждённых конкретных штаммов и доказанной пользы.
- Не создавать «универсальные» температуры для горячего или холодного ферментирования. Протокол привязан к конкретному виду продукта, субстрату, пищевым микроорганизмам, соли, времени, оборудованию и контролю.
- Не рекомендовать неизвестные бактерии, дикорастущую плесень или непищевые препараты. Особое внимание: тёплое хранение крахмалистых продуктов, сырой рыбы, мяса и анаэробных смесей в масле.
- Не выдавать показания журнала за подтверждение безопасности или готовности. При неясном источнике, невалидированных температурах и pH предупредить о рисках и предложить проверенный рецепт.
- Для конкретных численных значений проверять NCHFP, университетские extension-публикации и источники с документированной безопасностью. Базовый список в `docs/FERMENTATION.md`.
- Сохранять приватность журнала партий; `/delete_me` должен удалять партии и все замеры. Не запускать CI через GitHub Actions без необходимости.


## Управление проверенными технологическими протоколами

- Каталог `src/sushef/protocols.py` содержит источник, дату сверки, ID, версию карточки, рецептуру, этапы, диапазоны измерений и основания для остановки. Проверенный первоисточник не означает гарантии пищевой безопасности каждой партии.
- Нельзя менять пропорции, сроки, концентрации соли или уксуса по инициативе модели и по-прежнему называть технологию верифицированной. При изменении рецептуры нужен отдельный проверенный протокол.
- Нельзя использовать лабораторные/непищевые ферменты или неконтролируемые микроорганизмы; для кодзи и экзогенных ферментов необходимы пищевые SOP и параметры конкретных препаратов.
- В базе партия хранит `protocol_id` и `protocol_revision`. При смене версии автоматическая проверка старой партии должна отказываться работать, а не подменять данные.
- Решение о пригодности пищи не выводится только из pH, температуры, запаха, пузырьков или последнего сообщения. Даже `CHECK_SOURCE` не означает `SAFE`.
- Перед расширением каталога добавить source-backed тесты порогов и запретов в `tests/test_protocols.py`, затем проводить локальные тесты без GitHub Actions.


## Доказательная библиотека кодзи, ферментов и пищевых культур

- `src/sushef/science_library.py` — **только справочная информация по источникам**. `home_protocol_authorized` обязан быть `False` для всех карточек. Справочник не должен иметь кнопок запуска домашнего технологического процесса.
- **Кодзи:** обзор исследований с промышленными режимами НЕ превращать в домашний SOP, особенно при рисках Bacillus cereus и Staphylococcus aureus.
- **Ферменты:** для каждого препарата хранить точное торговое имя, производителя, физическую форму, применение и единицы активности/дозировки, если известны. Запрещено переносить дозы винодельческих ферментов на другие продукты или между жидкой и сухой формами. Если у препарата нет техпаспорта — дозу не выдумывать.
- **Закваски:** протокол King Arthur относится к созданию хлебной закваски, а не ко всей выпечке или пищевой безопасности сырого теста.
- **Пробиотики:** не обещать профилактику/лечение без точного штамма и клинических подтверждений; ISAPP различает ферментированные продукты и пробиотики.
- Все новые численные режимы связывать со ссылкой на производителя или научный источник и тщательно проверять применимость; свободный чат ClaudeHub не является независимой проверкой.


## Персональная память, приватность и БД

- Переключение режимов больше не очищает `Conversation`; история удаляется только явно через /reset или /delete_me. Не восстанавливайте старое поведение.
- Все новые сгенерированные рецепты сохраняются в `recipe_archive`, а не только в `users.last_recipe`. Старые сохранённые записи продолжают жить в `favorites`.
- Личная долговременная память только через `PersonalMemory` со статусом pending → active **после явного подтверждения пользователя**. Pending заметки и случайные просьбы на один ужин не отправлять как постоянные факты ClaudeHub.
- Счётчики повторяющихся негативных оценок — это наблюдения, а не подтверждённые личные предпочтения. Любые аллергены и ограничения имеют приоритет над привычками.
- `/export_my_data` должен выгружать все личные таблицы только конкретному Telegram ID и только в приватный чат. `/delete_me` удаляет `PersonalMemory` и `RecipeArchive` вместе с прежними данными; резервные копии требуют отдельной политики.
- Для PostgreSQL/SQLite использовать Alembic и резервную копию перед изменением схемы. Docker должен запускать `alembic upgrade head` перед ботом. Не выполнять принудительного пересоздания томов и не переносить SQLite→PostgreSQL без отдельной проверки сохранности данных.
- GitHub Actions — запрещённый по умолчанию путь для тестов и деплоя; только локальные тесты или доступный сервер. Не утверждать, что они прошли, если не выполнены.


## Пошаговый су-шеф и таймеры

- Рецепт может содержать `step_timers` (не более одной подсказки на шаг, 1–240 мин). Это **предложение**, а не самостоятельное действие агента: таймер запускается только после клика пользователя.
- В `CookingTimer` хранить `user_id`, частный `chat_id`, step_index, label, Unix due_at_ts, статус доставки и повторные попытки. Никакого хранения в RAM как единственного источника истины.
- Worker `timer_worker.py` проверяет просроченные таймеры в базе и отправляет Telegram-уведомления; без GitHub Actions, cron и дополнительных запросов ClaudeHub. Не утверждать exactly-once: после crash между send и commit возможна повторная доставка.
- Максимум 5 активных таймеров на человека, 1–240 минут. /timers показывает и позволяет отменять. Не допускать запуска таймера в групповых чатах или доступа чужого user_id.
- Таймеры сохраняются при переходе между шагами; отменяются при /reset, /delete_me, смене рецепта и аллергенов/исключений. Возобновление готовки для **того же** рецепта не сбрасывает шаг 0.
- Истечение времени — **НЕ** признак безопасной готовности мяса/рыбы/птицы и НЕ проверенная ферментационная технология. Автоматически переходить дальше запрещено.
- Схема БД требует Alembic revision `0002_timers` до запуска production, rollback не должен уничтожать пользовательские таймеры. Полное описание `docs/COOKING_TIMERS.md`.

- Сервер `155.212.162.47`, каталог `/opt/sushef`, Compose project name `sushef`, volume `sushef_pgdata`. Не изменять чужие Docker containers, volumes, Nginx и директории ServGo/AI Growth OS.

## Тон общения и персонализация (обязательно)
- При первом `/start` предлагать необязательное знакомство: желаемое имя/обращение, «ты/вы», четыре коротких примера одинакового кулинарного сценария и подтверждённый выбор тона.
- Обращение/стиль и тонкие комплименты должны быть индивидуальны, естественны и опираться на реальные действия; нельзя фантазировать об успехах или прошлых блюдах пользователя.
- Новичку — больше терпения и ориентиров по запаху/текстуре/времени, опытному — профессиональное общение на равных. Считывать контекст, не навешивать ярлык.
- Мягкий, соразмерный подход к безопасности: в обычных рецептах никаких автоматических назидательных оговорок; реальные существенные/критические риски называть ясно и кратко; специальные запреты ферментационных протоколов сохраняются.
- Долговременная память только с подтверждением, персональные настройки сохраняются в `users.preferences` и не привязаны к длительности чата. После `/reset` не теряются; `/delete_me` и `/export_my_data` работают для личных записей.
- Встроенное знакомство должно работать без дополнительных LLM-запросов. Во время реального деплоя нельзя обходить безопасную процедуру резервирования и локального `pytest`. GitHub Actions не запускать.


## Редакционная кулинарная библиотека (2026-10-09)
- `cuisine_catalog.py` содержит **реально сверенные источники**, каждый с издателем, URL, датой и уровнем полноты. `quantified` — источник привёл количественную раскладку; `reference` — культурно/технологическое описание без полной рецептуры. Не выдавать второе за первое.
- Бот использует `cuisine_recipes` (таблица общей библиотеки), а пользовательские `recipe_archive` и `personal_memories` остаются отдельными.
- Не копировать страницы сайтов и защищённые тексты книг целиком. Добавлять только независимо изложенные краткие технологические сведения, ссылку на источник и количественные данные; лицензии и условия повторного использования дополнительно проверять.
- Любой результат адаптации должен называться адаптацией и сохранять автора/URL исходной карточки. Нельзя менять технологические ограничения проверки ферментации; эти протоколы отдельно в `protocols.py`.
- Миграция `0003_cuisines` обязательна. Перед production-базой делать pg_dump и тест `alembic upgrade head` на копии. Запрет Actions сохраняется.
- `cuisine_matches` по словам не является фильтром безопасности по аллергенам и не доказывает совпадения рецепта с имеющимися продуктами.

## Профессиональная редакция v2
- Исходные количества продуктов: `source_amount` — это **не обязательно** закупочный вес брутто или готовый нетто. При отсутствии измерений `gross`, `net`, `trim_loss_percent`, `net_yield_grams`, `shelf_life_hours`, `nutrition_per_100g`, `cost_per_portion` оставлять null, не угадывать.

- Математический пересчёт на другие порции показывает число, но не валидирует технологию, соль, густоту, безопасность. Для неколичественных продуктов оставлять «по вкусу/желанию/консистенции».
- До производственного утверждения необходимы реальные пробные приготовления, брутто/нетто, выход и потеря, согласованные режимы и редакторское одобрение. UI не должен называть карточку утверждённой ресторанной ТТК.


## Telegram Bot API 10.3 и фирменный характер (2026-10-10)

- Четыре стиля должны оставаться очень почтительными и душевными. В уместных ответах обязательны разнообразные изысканные комплименты реальной идее, навыку, наблюдательности или вкусовому выбору; не выдавать неизвестные предпочтения или прошлые достижения за подтверждённую память.
- Сохранённые `cuisines`, `likes`, `textures` и активные личные заметки — основание для аккуратной персонализации. Аллергены и исключения имеют больший приоритет. При жалобе/прямом уточнении сперва ответить по существу.
- Native UI: aiogram>=3.31 для RichMessage 10.3, DisabledButton, force_reply, button styles, CopyTextButton, sendMessageDraft. Rich layout формировать только из экранированного текста. При подтверждённом TelegramBadRequest использовать HTML fallback; при timeout НЕ отправлять автоматически повторно во избежание дубликатов.
- Черновик 9.5/10.3 — лишь статус ожидания, не объявлять потоковым выводом ClaudeHub. Для новых рецептов карта содержит раскрываемые step_insights; старые рецепты должны остаться доступны.
- Прежде чем настраивать Mini App, нужен реальный HTTPS-hosting и проверка Telegram initData на сервере; не выдавать статический HTML или RichMessage за работающий JS-MiniApp.
- Не запускать Actions. Перед выкладкой: полный pytest, schema/backup/restore, Telegram/ClaudeHub smoke, проверка rollback после 0005 и компактной навигации.
