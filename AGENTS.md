# Правила для ИИ-разработчиков Sushef

1. **Приоритет:** безопасность еды и корректность рецептов важнее юмора, рекламы и правдоподобно звучащих выдумок.
2. Не создавайте фиктивных API-вызовов, не утверждайте, что тесты прошли без запуска; не заявляйте, что бот развернут без проверки Telegram.
3. Используйте ClaudeHub через конфигурацию. Не встраивайте токены, секреты, данные пользователей и пароли в код или issue.
4. Сохраните фирменный характер Сушефа: почтительный, тёплый, с частыми заслуженными комплиментами и добрым ненавязчивым юмором.
5. Соблюдайте предпочтения, явно указанные аллергены и противопоказания. Не советуйте спасать испорченную или опасную пищу. Для безопасности сначала точность, потом шутки.
6. Пользовательские записи привязаны к Telegram ID. Запретите доступ к чужим записям. Поддерживайте удаление пользовательских данных.
7. Прежде чем менять интерфейс, проверьте совместимость существующих callback_data с ботом. Тестируйте переходы, ошибки модели и JSON.
8. **GitHub Actions — дефицитный платный ресурс.** По умолчанию не используйте их для сборки, диагностики, тестов или деплоя. Выбирайте локальные средства, GitHub API и сервер. Никаких массовых запусков и тайных workflow. *Исключение с 2026-10-23: единственный разрешённый workflow — ручной `Deploy` (см. раздел «Ручной деплой через GitHub Actions» ниже).*
9. Для спорных архитектурных изменений создавайте PR с чётким описанием последствий. Не создавайте дополнительные внешние API-расходы без нужды.
10. Первый релиз — один экземпляр polling-бота. При масштабировании переходите на webhook, миграции Alembic, транзакционные квоты и очереди; не запускайте параллельные polling-процессы.

- При сопоставлении продуктов избегать угадывания единиц, синонимов и безопасности еды по названию: сомнительные случаи отдавать на проверку пользователю.
- При обновлении аллергенов нельзя продолжать приготовление по старому рецепту или недельному меню. Профиль влияет на все будущие рецепты.

## Обязательные правила ферментации

- Отдельно классифицировать микробную ферментацию и обработку **внешними ферментами**. Нельзя называть пищу пробиотической без подтверждённых конкретных штаммов и доказанной пользы.
- Не создавать «универсальные» температуры для горячего или холодного ферментирования. Протокол привязан к конкретному виду продукта, субстрату, пищевым микроорганизмам, соли, времени, оборудованию и контролю.
- Не рекомендовать неизвестные бактерии, дикорастущую плесень или непищевые препараты. Особое внимание: тёплое хранение крахмалистых продуктов, сырой рыбы, мяса и анаэробных смесей в масле.
- Не выдавать показания журнала за подтверждение безопасности или готовности. При неясном источнике, невалидированных температурах и pH предупредить о рисках и предложить проверенный рецепт.
- Для конкретных численных значений проверять NCHFP, университетские extension-публикации и источники с документированной безопасностью. Базовый список в `docs/FERMENTATION.md`.
- Сохранять приватность журнала партий; `/delete_me` должен удалять партии и все замеры. Не запускать CI через GitHub Actions без необходимости.


## Управление проверенными технологическими протоколами

- Каталог `src/sushef/protocols.py` содержит источник, дату сверки, ID, версию карточки, рецептуру, этапы, диапазоны измерений и основания для остановки. Проверенный первоисточник не означает гарантии пищевой безопасности каждой партии.
- Нельзя менять пропорции, сроки, концентрации соли или уксуса по инициативе модели и по-прежнему называть технологию верифицированной. При изменении рецептуры нужен отдельный проверенный протокол.
- Нельзя использовать лабораторные/непищевые ферменты или неконтролируемые микроорганизмы; для кодзи и экзогенных ферментов необходимы пищевые SOP и параметры конкретных препаратов.
- В базе партия хранит `protocol_id` и `protocol_revision`. При смене версии автоматическая проверка старой партии должна отказываться работать, а не подменять данные.
- Решение о пригодности пищи не выводится только из pH, температуры, запаха, пузырьков или последнего сообщения. Даже `CHECK_SOURCE` не означает `SAFE`.
- Перед расширением каталога добавить source-backed тесты порогов и запретов в `tests/test_protocols.py`, затем проводить локальные тесты без GitHub Actions.


## Доказательная библиотека кодзи, ферментов и пищевых культур

- `src/sushef/science_library.py` — **только справочная информация по источникам**. `home_protocol_authorized` обязан быть `False` для всех карточек. Справочник не должен иметь кнопок запуска домашнего технологического процесса.
- **Кодзи:** обзор исследований с промышленными режимами НЕ превращать в домашний SOP, особенно при рисках Bacillus cereus и Staphylococcus aureus.
- **Ферменты:** для каждого препарата хранить точное торговое имя, производителя, физическую форму, применение и единицы активности/дозировки, если известны. Запрещено переносить дозы винодельческих ферментов на другие продукты или между жидкой и сухой формами. Если у препарата нет техпаспорта — дозу не выдумывать.
- **Закваски:** протокол King Arthur относится к созданию хлебной закваски, а не ко всей выпечке или пищевой безопасности сырого теста.
- **Пробиотики:** не обещать профилактику/лечение без точного штамма и клинических подтверждений; ISAPP различает ферментированные продукты и пробиотики.
- Все новые численные режимы связывать со ссылкой на производителя или научный источник и тщательно проверять применимость; свободный чат ClaudeHub не является независимой проверкой.


## Персональная память, приватность и БД

- Переключение режимов больше не очищает `Conversation`; история удаляется только явно через /reset или /delete_me. Не восстанавливайте старое поведение.
- Все новые сгенерированные рецепты сохраняются в `recipe_archive`, а не только в `users.last_recipe`. Старые сохранённые записи продолжают жить в `favorites`.
- Личная долговременная память только через `PersonalMemory` со статусом pending → active **после явного подтверждения пользователя**. Pending заметки и случайные просьбы на один ужин не отправлять как постоянные факты ClaudeHub.
- Счётчики повторяющихся негативных оценок — это наблюдения, а не подтверждённые личные предпочтения. Любые аллергены и ограничения имеют приоритет над привычками.
- `/export_my_data` должен выгружать все личные таблицы только конкретному Telegram ID и только в приватный чат. `/delete_me` удаляет `PersonalMemory` и `RecipeArchive` вместе с прежними данными; резервные копии требуют отдельной политики.
- Для PostgreSQL/SQLite использовать Alembic и резервную копию перед изменением схемы. Docker должен запускать `alembic upgrade head` перед ботом. Не выполнять принудительного пересоздания томов и не переносить SQLite→PostgreSQL без отдельной проверки сохранности данных.
- GitHub Actions — запрещённый по умолчанию путь для тестов и деплоя; только локальные тесты или доступный сервер. Не утверждать, что они прошли, если не выполнены.


## Пошаговый су-шеф и таймеры

- Рецепт может содержать `step_timers` (не более одной подсказки на шаг, 1–240 мин). Это **предложение**, а не самостоятельное действие агента: таймер запускается только после клика пользователя.
- В `CookingTimer` хранить `user_id`, частный `chat_id`, step_index, label, Unix due_at_ts, статус доставки и повторные попытки. Никакого хранения в RAM как единственного источника истины.
- Worker `timer_worker.py` проверяет просроченные таймеры в базе и отправляет Telegram-уведомления; без GitHub Actions, cron и дополнительных запросов ClaudeHub. Не утверждать exactly-once: после crash между send и commit возможна повторная доставка.
- Максимум 5 активных таймеров на человека, 1–240 минут. /timers показывает и позволяет отменять. Не допускать запуска таймера в групповых чатах или доступа чужого user_id.
- Таймеры сохраняются при переходе между шагами; отменяются при /reset, /delete_me, смене рецепта и аллергенов/исключений. Возобновление готовки для **того же** рецепта не сбрасывает шаг 0.
- Истечение времени — **НЕ** признак безопасной готовности мяса/рыбы/птицы и НЕ проверенная ферментационная технология. Автоматически переходить дальше запрещено.
- Схема БД требует Alembic revision `0002_timers` до запуска production, rollback не должен уничтожать пользовательские таймеры. Полное описание `docs/COOKING_TIMERS.md`.


## Codespaces → production без Actions

- Использовать `scripts/deploy_via_codespaces.sh` только из Codespace **grunvald91/Sushef** на ветке `feat/guided-cooking-timers`; скрипт проверяет SHA, установку Python, `pytest`, SSH, отдельный Docker-проект, создание бэкапа, схему и health-check.
- Сервер адрес из секрета `SUSHEF_SERVER_HOST`, каталог `/opt/sushef`, Compose project name `sushef`, volume `sushef_pgdata`. Не изменять чужие Docker containers, volumes, Nginx и директории ServGo/AI Growth OS.
- Секреты получать только из защищённого окружения Codespaces `SERVER_SSH_KEY`, `TELEGRAM_BOT_TOKEN`, `CLAUDEHUB_API_KEY`, не читать Actions secrets и не логировать значения. Если секреты недоступны, НЕ пытаться вытащить их обходным способом.
- Первым проверять тесты; при существующем volume перед миграцией обязательно `pg_dump -Fc`, и запрещено мигрировать без проверенной резервной копии. При ошибке НЕ удалять том.
- Не включать автодеплой в `postCreateCommand`/GitHub Actions. Production меняется только после ручного запуска VS Code Task и его успешного выполнения.
- После Docker-start дополнительно выполнить минимальные Telegram и ClaudeHub проверки (один тестовый LLM запрос), затем ручной smoke test recipe/timer. Только тогда заявлять production healthy. Подробности `docs/CODESPACES_DEPLOY.md`.


## Тон общения и персонализация (обязательно)
- При первом `/start` предлагать необязательное знакомство: желаемое имя/обращение, «ты/вы», четыре коротких примера одинакового кулинарного сценария и подтверждённый выбор тона.
- Обращение/стиль и тонкие комплименты должны быть индивидуальны, естественны и опираться на реальные действия; нельзя фантазировать об успехах или прошлых блюдах пользователя.
- Новичку — больше терпения и ориентиров по запаху/текстуре/времени, опытному — профессиональное общение на равных. Считывать контекст, не навешивать ярлык.
- Мягкий, соразмерный подход к безопасности: в обычных рецептах никаких автоматических назидательных оговорок; реальные существенные/критические риски называть ясно и кратко; специальные запреты ферментационных протоколов сохраняются.
- Долговременная память только с подтверждением, персональные настройки сохраняются в `users.preferences` и не привязаны к длительности чата. После `/reset` не теряются; `/delete_me` и `/export_my_data` работают для личных записей.
- Встроенное знакомство должно работать без дополнительных LLM-запросов. Во время реального деплоя нельзя обходить безопасную процедуру резервирования и локального `pytest`. GitHub Actions не запускать.


## Редакционная кулинарная библиотека (2026-10-09)
- `cuisine_catalog.py` содержит **реально сверенные источники**, каждый с издателем, URL, датой и уровнем полноты. `quantified` — источник привёл количественную раскладку; `reference` — культурно/технологическое описание без полной рецептуры. Не выдавать второе за первое.
- Бот использует `cuisine_recipes` (таблица общей библиотеки), а пользовательские `recipe_archive` и `personal_memories` остаются отдельными.
- Не копировать страницы сайтов и защищённые тексты книг целиком. Добавлять только независимо изложенные краткие технологические сведения, ссылку на источник и количественные данные; лицензии и условия повторного использования дополнительно проверять.
- Любой результат адаптации должен называться адаптацией и сохранять автора/URL исходной карточки. Нельзя менять технологические ограничения проверки ферментации; эти протоколы отдельно в `protocols.py`.
- Миграция `0003_cuisines` обязательна. Перед production-базой делать pg_dump и тест `alembic upgrade head` на копии. Запрет Actions сохраняется.
- `cuisine_matches` по словам не является фильтром безопасности по аллергенам и не доказывает совпадения рецепта с имеющимися продуктами.


## Профессиональные технологические карты и воспроизводимость

- Библиотека техники: src/sushef/technique_catalog.py, таблица culinary_techniques. Библиотека конкретных блюд: src/sushef/dish_process_cards.py, таблица dish_process_cards.
- Сохраняйте ссылку на научно-кулинарный источник и разграничивайте фактические ингредиенты/этапы источника от редакционных объяснений механизмов и рекомендаций исправления.
- Не приписывайте источнику неизвестный выход, температурные режимы, универсальные сроки, разрешения на небезопасную ферментацию и не называйте редакционную карту сертифицированной производственной ТТК.
- В новой модели step_insights должны быть привязаны к действительным индексам шагов, иметь ограниченную длину и оставаться необязательными для старых архивных рецептов.

- Перед развёртыванием миграции 0004_techniques: резервная копия БД, локальный pytest, проверка idempotent seed, Telegram и ClaudeHub smoke. Не трогайте другие Docker-проекты. GitHub Actions по умолчанию запрещены.

## Профессиональная редакция v2
- Исходные количества продуктов: `source_amount` — это **не обязательно** закупочный вес брутто или готовый нетто. При отсутствии измерений `gross`, `net`, `trim_loss_percent`, `net_yield_grams`, `shelf_life_hours`, `nutrition_per_100g`, `cost_per_portion` оставлять null, не угадывать.
- Записанные v1 техкарты не переписывать: v2 — отдельные ID, миграция `0005_prod_cards`. Пользовательские данные не затрагиваются.
- Математический пересчёт на другие порции показывает число, но не валидирует технологию, соль, густоту, безопасность. Для неколичественных продуктов оставлять «по вкусу/желанию/консистенции».
- До производственного утверждения необходимы реальные пробные приготовления, брутто/нетто, выход и потеря, согласованные режимы и редакторское одобрение. UI не должен называть карточку утверждённой ресторанной ТТК.


## Telegram Bot API 10.3 и фирменный характер (2026-10-10)

- Четыре стиля должны оставаться очень почтительными и душевными. В уместных ответах обязательны разнообразные изысканные комплименты реальной идее, навыку, наблюдательности или вкусовому выбору; не выдавать неизвестные предпочтения или прошлые достижения за подтверждённую память.
- Сохранённые `cuisines`, `likes`, `textures` и активные личные заметки — основание для аккуратной персонализации. Аллергены и исключения имеют больший приоритет. При жалобе/прямом уточнении сперва ответить по существу.
- Native UI: aiogram>=3.31 для RichMessage 10.3, DisabledButton, force_reply, button styles, CopyTextButton, sendMessageDraft. Rich layout формировать только из экранированного текста. При подтверждённом TelegramBadRequest использовать HTML fallback; при timeout НЕ отправлять автоматически повторно во избежание дубликатов.
- Черновик 9.5/10.3 — лишь статус ожидания, не объявлять потоковым выводом ClaudeHub. Для новых рецептов карта содержит раскрываемые step_insights; старые рецепты должны остаться доступны.
- Прежде чем настраивать Mini App, нужен реальный HTTPS-hosting и проверка Telegram initData на сервере; не выдавать статический HTML или RichMessage за работающий JS-MiniApp.
- Не запускать Actions. Перед выкладкой: полный pytest, schema/backup/restore, Telegram/ClaudeHub smoke, проверка rollback после 0005 и компактной навигации.


## Реальный диалог и богатое оформление (10.10.2026)

- Нельзя оставить обычный `chef.answer` на старом `send_text`: использовать `send_dialogue` и native Rich Markdown с безопасным HTML fallback. Без автоматической повторной отправки при неопределённой ошибке сети.
- Развёрнутые рецепты в чатах должны содержать читаемые разделы, списки и отдельные этапы. Исправлять склейки вроде `15 минут.2. Овощи` без изменения цифр и рецептуры. Форматирование отделено от пищевых рекомендаций.
- Если в ответе есть продукты и шаги, кнопка `dialogue:recipe:<sha256-prefix>` предлагает конвертацию по отдельному нажатию с использованием ПОСЛЕДНЕГО запроса и ответа, проверкой хэша, AI-квоты и обычным `Chef.recipe`. Конвертация обязана учитывать подтверждённые ограничения и не должна выдавать текстовую оценку готовности за измерение.
- Комплименты — регулярные, изысканные и разнообразные, но только с подтверждённым основанием; не приветствовать старого собеседника как нового каждый раз и не выдумывать продукты, прошлую память или показания температуры. Для обычной домашней рыбы безопасный ориентир 63 °C по термометру.
- Деплой только через Codespaces и SSH, после полного pytest, бэкапа, восстановления и Telegram/ClaudeHub smoke. GitHub Actions не использовать.


## Поддержка, инструкция и Telegram Stars (2026-10-18)

- Кнопки «📖 Инструкция» и «🛟 Поддержка» есть в главном меню и в «Все возможности»; /help и /guide показывают инструкцию без запросов к ИИ.
- Обращения хранятся в `support_tickets`/`support_messages` и доставляются сотрудникам из `SUPPORT_ADMIN_IDS` и `support_admins`. Username `SUPPORT_ADMIN_USERNAME` действует только при пустом `SUPPORT_ADMIN_IDS` и закрепляется лишь за первым аккаунтом; не ослабляйте эту проверку. Сотрудник отвечает реплаем на карточку обращения или кнопкой «Ответить»; /tickets — открытые обращения.
- Оплата — только Telegram Stars (`XTR`, без provider_token). Доступ продлевается в `subscriptions` исключительно после `successful_payment`; `charge_id` уникален, повторная доставка не продлевает дважды. pre_checkout проверяет пользователя, цену и срок счёта.
- Платный только запрос к ИИ: рецепты, история, продукты, таймеры, инструкция и поддержка остаются бесплатными. Пробные запросы `FREE_TRIAL_REQUESTS` списываются вместе с дневной квотой. Дневной лимит действует и для освобождённых ID (`PAYMENT_EXEMPT_IDS`, сотрудники поддержки).
- /delete_me удаляет обращения, но сохраняет срок подписки и записи о платежах для возвратов. Возврат — /refund <charge_id> у сотрудника, через `refundStarPayment`.
- Миграция `0006_support_billing` только добавляет таблицы. Откат кода: `alembic stamp 0005_prod_cards` и прежний образ; downgrade запрещён, чтобы не потерять платежи.


## Кнопки-действия, сохранение рецептов и современный Telegram UI (2026-10-18)

- Кнопка обязана выполнять действие сразу. Если нужен свободный ввод, рядом всегда есть готовые варианты (`quick:*`), которые запускают запрос без набора текста. Не добавляйте кнопки, которые только объясняют, какую команду написать.
- Под каждым рецептом: «❤️ В избранное» и «📖 В мои рецепты». Кнопки карточки содержат id архива (`archive:fav:<id>`) и сохраняют именно этот рецепт, а не последний. Под ответом диалога (`dialogue:fav|save:<tag>`) ClaudeHub делает выжимку в формате карточки; повторное нажатие не вызывает модель и не создаёт дубликатов. Выжимка тратит дневной лимит, но не пробные запросы.
- Во время пробного периода после КАЖДОГО ответа ИИ отправляется предложение месячной подписки с кнопкой `pay:buy`; оплатившим и освобождённым — не показывается.
- Текст для копирования — в `коде` или ```блоке```: `telegram_html` превращает его в `<code>/<pre>`. Таблицы Markdown в обычном HTML — моноширинный блок; в rich-сообщениях — нативный `InputRichBlockTable` (`rich_blocks.py`), списки `- [ ]` — пункты с галочками.
- `TELEGRAM_STREAM_ANSWERS`: ответ диалога показывается по мере генерации через `sendRichMessageDraft` (поток ClaudeHub `messages.stream`). Черновик временный, итог всегда отправляется обычным сообщением; при недоступности потока — обычный запрос без потери ответа.
- Эффект 🎉 (`message_effect_id`) только на сообщении об успешной оплате. Изображения в ответы не добавляются: у проекта нет проверенного источника картинок, генерировать или подставлять чужие фото нельзя.


## Inline-режим «Сушеф в любом чате» (2026-10-18)

- `inline_mode.py`: `@бот вопрос` в любом чате. Доступ только у оплативших и освобождённых (`PAYMENT_EXEMPT_IDS`, поддержка); пробные запросы на inline не действуют. Проверка повторяется в `chosen_inline_result`.
- ИИ не вызывается на каждое нажатие клавиши: выдача содержит заготовку «Спросить Сушефа», ответ генерируется после выбора результата и вставляется через `editMessageText(inline_message_id)`. Тратит дневной лимит. Без inline-клавиатуры у результата Telegram не вернёт `inline_message_id` — не убирайте её.
- В выдаче также свои рецепты из архива (без ИИ). Чужие данные в выдачу не попадают: `is_personal=True`.
- В BotFather обязательно: `/setinline` (placeholder, например «Спросите шефа…») и `/setinlinefeedback` → 100%. Без этого inline-запросы или их выбор не придут боту.

- Bot API 10.3: черновик ответа отправляется с `can_stop=True`; `Update.stopped_message_generation` останавливает поток ClaudeHub, пользователь получает уже написанную часть с пометкой «Остановлено».
- Guest mode (Bot API 10.0): `Update.guest_message` → `answerGuestQuery` с заготовкой, затем правка по `inline_message_id`. Те же правила доступа, что у inline.
- Сверено со справкой Bot API 10.3 (18.10.2026): ломающие изменения 9.0–10.3 (эфемерные параметры, `correct_option_ids`, подарки, `BusinessConnection.rights`) код Сушефа не затрагивают.


## Видимая реакция на запрос и модель по умолчанию (2026-10-23)

- На любой запрос к ИИ (вопрос, рецепт, меню, выжимка, конвертация, фото) человек сразу видит три сигнала: реакцию 👀 на своё сообщение, черновик с кулинарной фразой и поддерживаемое «печатает…» (`ChefWorking` в `telegram_modern.py`). Реакция снимается, когда ответ готов; на собственные сообщения бота с кнопками она не ставится. Отключается `TELEGRAM_SEEN_REACTION` и `TELEGRAM_DRAFT_PREVIEW`.
- Текст черновика — живые кулинарные фразы из `kitchen_phrases.py` по режиму (рецепт, меню, ферментация, спасение блюда, вопрос, фото), с учётом «ты/Вы». Фраза сменяется каждые ~5 секунд и замолкает, как только начинается поток ответа. Фразы — только статус ожидания: без технологических советов, температур, обещаний безопасности и выдуманных фактов о пользователе; в научных режимах без шуток.
- `ChefWorking.stop()` вызывается сразу после ответа модели, ДО отправки ответа, чтобы статус не мелькнул под готовым ответом; повторный вызов безопасен.
- Индикатор — украшение: любая его ошибка пишется в лог как warning и НЕ ломает и не повторяет ответ. Ошибки черновика и потока больше не прячутся на уровне debug.
- Модель ClaudeHub по умолчанию — `claude-haiku-5-5`. Реальное значение на сервере задаёт `CLAUDEHUB_MODEL`; идентификатор в ClaudeHub нужно проверить одним тестовым запросом до выкладки, он может называться иначе.


## Публичный репозиторий и ручной деплой через GitHub Actions (2026-10-23)

- Репозиторий публичный ради безлимитных минут Actions. Поэтому в нём нельзя хранить ничего приватного: ключи, токены, пароли, адрес сервера. Адрес сервера — секрет `SUSHEF_SERVER_HOST`; в коде и документации его нет. Telegram-ID администраторов и username — не учётные данные, остаются значениями по умолчанию в `config.py`, потому что серверный `.env` их не переопределяет.
- Единственный workflow — `.github/workflows/deploy.yml`, только `workflow_dispatch` (кнопка). Запрещено добавлять триггеры `push`, `pull_request`, `pull_request_target`, `schedule` и т. п.: в публичном репозитории чужой код не должен получать секреты. Другие workflow — только по отдельному решению владельца.
- Секреты Actions: `SERVER_SSH_KEY`, `SUSHEF_SERVER_HOST`, `TELEGRAM_BOT_TOKEN`, `CLAUDEHUB_API` (в workflow он передаётся скрипту как `CLAUDEHUB_API_KEY`); необязательный `SERVER_HOST_KEY` — строка known_hosts сервера, закрепляет отпечаток. Не печатать значения в логах.
- Workflow запускает тот же `scripts/deploy_via_codespaces.sh`: тесты → бэкап БД → выкладка → smoke Telegram/ClaudeHub. Правила про бэкап, чужие Docker-проекты и «успех только с DEPLOYED_OK» остаются в силе. Подробности — `docs/ACTIONS_DEPLOY.md`.
- Поле `set_model` меняет `CLAUDEHUB_MODEL` в уже существующем серверном `.env` (копия старого файла сохраняется рядом).


## Характер Сушефа на Haiku (2026-10-23)

- `PERSONA` в `prompts.py` заканчивается блоком «ЯДРО ХАРАКТЕРА СУШЕФА»: вступление с изысканным образным откликом на то, что человек написал, суть блюда, точный рецепт (граммы, штуки, время, наблюдаемые признаки готовности), «Тонкости вкуса», тёплое завершение. Блок и два примера нужны, чтобы компактная модель держала тот же характер, что и крупная.
- Комплимент выбору, который виден в сообщении (сочетание продуктов, идея, вопрос, вкусовой замысел), — достаточное основание. Запрещено выдумывать то, чего человек не говорил: прошлые блюда, успехи, «как всегда», любимые специи, историю знакомства.
- Примеры в блоке не должны совпадать с блюдами из сравнительных проверок моделей, чтобы тест не превращался в проверку копирования.


## Законченные ответы и память темы (2026-10-23)

- Ответ диалога не должен обрываться на полуслове. `Chef` смотрит `stop_reason`: если ответ упёрся в `max_tokens`, он дописывает продолжение (до двух раз, и в потоке, и в обычном запросе); остаток всё равно обрезается до конца предложения. Лимит по умолчанию — `MAX_OUTPUT_TOKENS=8192`; серверный `.env` может задавать своё значение, продолжение работает при любом.
- Стоп пользователя во время продолжения не глотается: исключение показа пробрасывается, глотаются только ошибки API.
- В `PERSONA` — «ПАМЯТЬ РАЗГОВОРА»: список продуктов после названного блюда улучшает ЭТО блюдо, а не заменяет его. На открытый запрос блюда рецепт даётся сразу, а в конце задаётся один вопрос о том, какие продукты и вкусы есть у человека.
