# Развёртывание Сушефа через GitHub Codespaces без GitHub Actions

**Целевой сервер:** `155.212.162.47` (SSH `root` по ранее работавшему ключу), **проект:** `grunvald91/Sushef`, **ветка:** `feat/cuisine-knowledge-audit-20261009`.

Скрипт предназначен для запуска **в Codespace репозитория Sushef**, не в Codespace Ai_growth_os. Он не использует GitHub Actions и не меняет ServGo, AI Growth OS и другие серверные проекты.

## Почему автоматического развёртывания при открытии Codespace нет

Развёртывание меняет живой сервер и базу данных. Поэтому `.devcontainer/devcontainer.json` только готовит Python/SSH, а запуск production оставлен явной задачей `.vscode/tasks.json`:

**Сушеф: Тесты + деплой на сервер 155**

Выберите её в Codespace через палитру VS Code: **Terminal → Run Task → Сушеф: Тесты + деплой на сервер 155**. Задача выполняет `bash scripts/deploy_via_codespaces.sh`. Код копировать вручную и отправлять ключи в чат не нужно.

## 1. Codespaces и доступ к секретам

Откройте на GitHub `grunvald91/Sushef`, выберите ветку `feat/cuisine-knowledge-audit-20261009`, затем **Code → Codespaces → Create codespace on feat/cuisine-knowledge-audit-20261009**. Ранее использовавшийся Codespace `silver-space-winner-r467jjq6q695cxr77.github.dev` относился к другому проекту; нужная задача находится в репозитории Sushef.

В **GitHub Settings → Codespaces → Secrets → New secret** должны быть доступны именно этому репозиторию:

| Secret | Значение |
|---|---|
| `SERVER_SSH_KEY` | Исправленный *приватный* SSH-ключ, которым ранее успешно вошли на сервер 155.212.162.47 |
| `TELEGRAM_BOT_TOKEN` | Токен **отдельного** Telegram-бота Sushef |
| `CLAUDEHUB_API_KEY` | Ключ ClaudeHub для обращения к модели |

Не публикуйте значения в Issues, PR, Telegram, чате или переменных репозитория. GitHub **Actions Secrets** и **Codespaces Secrets** — разные области доступности; секреты из Ai_growth_os тоже могут требовать явного разрешения для Sushef. Если секреты добавлены во время работы Codespace, его нужно перезапустить для применения.

Необязательные Codespaces-секреты/переменные: `POSTGRES_PASSWORD` (только латинские буквы, цифры, подчёркивание или дефис), `CLAUDEHUB_MODEL` (проверенный доступный идентификатор модели), `SUSHEF_SERVER_HOST` (по умолчанию 155.212.162.47), `SUSHEF_SERVER_USER` (по умолчанию root), `SUSHEF_SERVER_PORT` (по умолчанию 22).

SSH использует отдельную 0600-копию приватного ключа только на время деплоя (удаляется автоматически) и `StrictHostKeyChecking=accept-new`. Новый SSH-host key при первом подключении доверяется по принципу TOFU. **В идеале заранее сверьте отпечаток SSH host key из ранее доверенного подключения**; изменение уже известного ключа приведёт к ошибке и отказу от подключения.

## 2. Что выполнится без ручных команд

1. Проверка ветки и «чистоты» коммита, чтобы тестировать и выкладывать **одну и ту же версию**.
2. Установка Python-зависимостей в локальную `.venv` Codespace, `compileall` и **полный `pytest -q`**. Любая ошибка прекращает процесс ДО подключения к production.
3. Проверка SSH-подключения и наличия Docker Compose на сервере.
4. Проверка `/opt/sushef` и безопасного изолированного пути.
5. Если `/opt/sushef/shared/.env` **уже существует**, он сохраняется без изменения. При первой установке создаётся закрытый файл с секретами из Codespaces и новым PostgreSQL-паролем.
6. Отправка **только** `git archive HEAD` в `/opt/sushef/releases/<commit-sha>`. Серверу не нужны права чтения приватного GitHub-репозитория.
7. При существующей БД `sushef_pgdata` скрипт **обязательно** делает `pg_dump -Fc` и проверяет структуру архива. Если бэкап невозможен — обновление **не происходит**. Бэкапы остаются в `/opt/sushef/backups/` с закрытыми правами.
8. Сборка бот-контейнера только проекта `sushef` и `docker compose --project-name sushef up -d`.
9. Dockerfile применяет Alembic до polling (`0001_memory`, `0002_timers`, `0003_cuisines`), сохраняя существующие данные; бот дополнительно проверяет текущую версию схемы.
10. Проверка устойчивого запуска контейнера. При немедленном падении скрипт пытается вернуть **предыдущую версию кода**, не делает опасный откат схемы и не удаляет БД.

**Существующие сервисы:** никакие команды `docker system prune`, `docker compose down -v`, изменение Nginx, глобальные обновления пакетов и перезапуск других контейнеров не используются. Sushef использует собственный Compose-проект/том/каталог и не публикует порт наружу.

## 3. Что проверять после запуска

В личном чате Telegram с ботом Sushef:

- `/start` — меню;
- создать рецепт из продуктов — должен сохраниться в `/recipes`;
- добавить и подтвердить факт через `/remember`, проверить `/memory`;
- `/ferment` — технологические протоколы и научная библиотека;
- «Готовим пошагово» → таймер 1 мин → `/timers` → ожидать сообщения;
- отправить обычный вопрос — **отдельно подтвердить реальную работу ClaudeHub API**.

Успех Docker-контейнера не подтверждает работоспособность ClaudeHub-модели. Скрипт не объявляет систему готовой без этого smoke-теста.

## 4. Предсказуемые блокировки

- Нет `SERVER_SSH_KEY` или он не разрешён Codespace Sushef → SSH остановится, никакие серверные изменения не делаются.
- Нет `TELEGRAM_BOT_TOKEN`/`CLAUDEHUB_API_KEY` при первой установке → не создаётся production `.env`.
- Недоступен GitHub/PyPI/Docker registry или падают тесты → **деплой прекращается**.
- На сервере уже есть несвязанная директория/том `sushef` → конфликт, не перезаписывать данные.
- PostgreSQL-том существует, но действующая БД недоступна для бэкапа → безопасная остановка.
- Если сервер перестал работать **после** миграции, может потребоваться ручное восстановление из бэкапа (автоматический rollback БД опасен).

## 5. Что не делает скрипт

- Не тратит минуты GitHub Actions и не создаёт workflow.
- Не извлекает уже сохранённые секреты GitHub Actions API.
- Не развёртывает без работающего Codespace и SSH-доступа.
- Не запускает вторую копию Telegram polling-бота с тем же токеном в другом месте.
- Не выполняет финансово затратные ClaudeHub-запросы автоматически без необходимости.
- Не шифрует и не отправляет копии PostgreSQL-бэкапа на независимое защищённое хранилище: для production нужно отдельно настроить off-site backup, срок хранения и проверку восстановления.

**Важно:** подготовленные коммиты и задача VS Code не доказывают, что сервер обновлён. Реальный результат появляется только после успешного выполнения задачи в Codespace и ручной проверки Telegram/ClaudeHub.


### Актуальное дополнение к проверке перед релизом

После проверки стабильности Docker-контейнера сценарий запускает `python -m sushef.smoke` **внутри контейнера**, который делает Telegram `get_me()` и **один короткий запрос к ClaudeHub**. Это подтверждает валидность двух API-ключей и доступность выбранной LLM-модели на момент теста; запрос может незначительно расходовать средства ClaudeHub. При ошибке смоук-теста новый выпуск не помечается успешным, выполняется попытка восстановления предыдущего кода либо остановка нового бота. База не удаляется.

При настройке ключа убедитесь, что `CLAUDEHUB_MODEL` соответствует *доступной в вашем аккаунте ClaudeHub* модели. Значение по умолчанию в проекте ещё не доказано рабочим.

`/cancel` отменяет **только текущий ввод**, не удаляет таймеры. `/reset` прекращает готовку и отменяет таймеры — отдельная команда.
